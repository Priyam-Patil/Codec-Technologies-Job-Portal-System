# Browser debugging and repair — 21 November 2026

Existing architecture and integrations retained. No environment file, deployment, remote or production record was changed.

| Initial problem | Root cause | Repair | Evidence |
|---|---|---|---|
| Real Clerk login succeeded but candidate profile returned 404 | Candidate APIs depended entirely on a webhook-created MongoDB user; localhost receives no webhook | Authenticated APIs initialize a missing profile from server-verified Clerk identity, using an idempotent insert that preserves existing edits | Independently reproduced 404 before repair; live unseeded Clerk journeys and concurrent bootstrap integration test pass |
| Skills were not visible immediately after resume submission | Upload updated metadata but offered no extracted-skill summary; a second profile request could fail independently | Upload returns updated user; Applications immediately renders PDF-only skills, experience hint, processing result and comparison link | Browser tests clear manual skills, upload a real PDF, assert React/Node.js/MongoDB immediately and after reload |
| Damaged PDF accepted as generic unreadable fallback | Parser collapsed invalid/encrypted PDFs into the scanned-document fallback | Distinguish invalid/encrypted input; reject with 422 before uploading | Damaged PDF rejected through normal browser form; parser unit test passes |
| Apply intermittently reported login required during a valid session | Clickable button rendered before authenticated profile finished loading | Wait for Clerk session restoration and profile readiness before enabling Apply | Reproduced with fresh browser navigations; normal application regression journey |
| A filter selected just after reload reset itself | Provider identity key remounted the entire application when Clerk finished restoring its session | Delay initial application render until Clerk is loaded; keep identity isolation | Hide-applied regression now exercises hard navigation followed immediately by checkbox selection |
| Recruiter changed status but candidate still saw Pending | Application history was only loaded at initial context creation | Refresh on page entry, window focus, explicit refresh and every 30 seconds | Recruiter rejects, refreshes, candidate navigates to history without a hard reload and sees Rejected |
| Invalid recruiter token could briefly render protected children | Route checked only token presence | Verify company identity before rendering recruiter dashboard; expired/invalid tokens cleared | Browser protected-route and invalid-token checks |
| Failed private-data requests resembled empty lists or endless loading | No persistent error state or retry controls | Separate profile/company/applications/jobs/applicants error states and recovery controls | Jobs 503 fault injection followed by real API retry; protected routes and page checks |
| Search Enter and Clear were inconsistent | Hero inputs were uncontrolled and lacked submit semantics | Controlled shared search state and a real search form | Search Enter/clear browser regression |
| Edit job could display old data during route changes/failures | Previous job state reused across parameter changes | Associate state with request key, abort superseded requests and show retry/back controls | Existing edit journey passes; cancellation implementation inspected |
| Recruiter modal lacked keyboard containment and logo feedback | No focus management; weak client upload feedback | Focus trap/Escape/focus restoration, scrolling modal and aligned image checks | Invalid login, required fields, logo upload and keyboard browser checks |
| Normal frontend API unavailable | Existing frontend targets port 5000; configured database prevents normal server startup, while old demo uses a different API port | Added explicit persistent local development mode on 5000, using a guarded local MongoDB directory and normal frontend on 5175 | Real recruiter registration, job creation, resume upload, application and status workflow through normal client configuration |

Important files: `client/src/context/AppContext.jsx`, `client/src/pages/Applications.jsx`, `ApplyJob.jsx`, `CandidateHub.jsx`, `EditJob.jsx`, `ManageJobs.jsx`, `ViewApplications.jsx`, `components/Hero.jsx`, `components/RecruiterLogin.jsx`, `client/src/App.jsx`; `server/controllers/userController.js`, `utils/candidateProfile.js`, `utils/resumeWorker.js`, `app.js`, `config/db.js`, `scripts/dev-local.js`.

No new collection or destructive migration was required. The persistent local mode provisions the application uniqueness index only for an empty local application collection. Existing populated databases are not migrated automatically. Environment files and variable values on disk remain unchanged.

Test corrections were kept separate from application defects: scoped ambiguous Next/alert selectors, reloaded the UI after direct bookmark API setup, and scoped repeated status labels. These changes do not replace application requests with mocked success data.

The replacement-upload test now waits for the profile's Edit button or file input before choosing a file. A previous immediate visibility probe raced profile loading on mobile. Screenshot helpers dismiss transient notifications and return to the page top so sticky navigation does not obscure full-page evidence.

During failure analysis, Playwright included a generated QA password in a local failure snapshot. The affected artifacts were sanitized and the disposable audit run's accounts/database were removed and replaced, invalidating that credential. Test helpers now clear submitted password inputs before later failure snapshots. Environment values and production credentials were not exposed. Trace/video recording remains disabled.
